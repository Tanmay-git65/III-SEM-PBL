---------------------------------------------------------------------
1. WHAT THE PROGRAM DOES
---------------------------------------------------------------------

Maze Lab generates random mazes, lets you play them, and solves them.

  - Two generators:  Randomized DFS, and Kruskal's algorithm
  - Two solvers:     BFS (breadth-first search), and A* (A-star)
  - Play mode:       move a player from start to exit, then see your
                     moves, time, and efficiency against the shortest path
  - Compare mode:    run BFS and A* on the same maze and compare path
                     length, cells expanded, and time
  - Validation:      13 automatic correctness tests
  - Benchmark:       400 mazes, averages printed for both solvers

It has two front ends that share the same core code:
  - a text (console) menu
  - a graphical window (Windows uses Win32 API, Linux uses X11)

No external libraries are used. Only the C++ standard library and the
operating system's own window functions.


---------------------------------------------------------------------
2. HOW TO BUILD AND RUN
---------------------------------------------------------------------

Open PowerShell in the src_code folder of your copy of the repo, e.g.:

    cd III-SEM-PBL\src_code

Build (needed the first time and after every edit):

    g++ -std=c++17 main.cpp -o maze.exe -lgdi32

  -std=c++17   use the C++17 standard
  main.cpp     the only .cpp file; it includes all the .hpp files
  -o maze.exe  name of the program to create
  -lgdi32      link the Windows graphics library (needed for the window)

Run:

    .\maze.exe               console menu (option 9 opens the window)
    .\maze.exe --gui         open the window directly
    .\maze.exe --benchmark   print benchmark results and exit

Window controls:
    1 / 2      generate maze (DFS / Kruskal)
    3          start or stop play mode
    W A S D    move (arrow keys also work); Esc or Q stops playing
    4 / 5      solve with BFS / A*
    6          compare BFS and A*
    7          run validation tests (option 8 in the console menu)
    - / +      buttons that change rows and columns

Console controls: type the menu number and press Enter. In play mode
type W, A, S or D and press Enter; Q quits.

Problems:
  "g++ is not recognized"  g++ is not on PATH. It is installed in
                           C:\mingw64\bin on the development machine.
  Change does not appear   you did not rebuild after editing.
  "main.cpp: No such file" you are not inside the src_code folder.

3. FILES AT A GLANCE
---------------------------------------------------------------------

  main.cpp          Program entry point. Chooses console, window, or
                    benchmark mode.
  settings.hpp      EVERY colour, label, symbol, key, and size. Edit
                    this file for visual or text changes.
  maze.hpp          The maze data: grid of cells and their walls.
  disjoint_set.hpp  Union-find structure used by Kruskal's generator.
  generators.hpp    DFS and Kruskal maze generators.
  solvers.hpp       BFS and A* solvers.
  player.hpp        The player in play mode: position, moves, timer.
  session.hpp       Holds the current maze plus one of each generator
                    and solver; shared by console and window.
  validation.hpp    The 13 correctness tests.
  benchmark.hpp     Runs 400 mazes and prints average results.
  console_ui.hpp    The text menu and the text drawing of the maze.
  gui_app.hpp       What the window shows and how it reacts to input.
                    Does not touch the operating system directly.
  gui_window.hpp    Opens the real window (Win32 or X11), passes input
                    to gui_app.hpp, and paints its drawing.

Which file includes which:

  main.cpp
   |-- session.hpp ------ maze.hpp, generators.hpp, solvers.hpp, settings.hpp
   |-- console_ui.hpp --- settings, session, player, validation
   |-- gui_window.hpp --- gui_app.hpp --- settings, session, player, validation
   '-- benchmark.hpp ---- generators.hpp, solvers.hpp

  generators.hpp --- maze.hpp, disjoint_set.hpp
  solvers.hpp ------ maze.hpp
  player.hpp ------- maze.hpp
  validation.hpp --- maze, disjoint_set, generators, solvers, player

Why only .hpp files? The project is "header-only": there is one .cpp
(main.cpp) and every other file is included into it, so it compiles as
a single unit and the build command stays one line. Every header starts
with "#pragma once" so it is included only once even if several files
include it. Free functions in headers are marked "inline" so the project
would still link correctly if more .cpp files were added later.


---------------------------------------------------------------------
4. HOW THE PIECES FIT TOGETHER
---------------------------------------------------------------------

Layers, from bottom to top:

  [settings.hpp]  values only, used by the layers above

  [maze.hpp] [disjoint_set.hpp]         data structures
        |
  [generators.hpp] [solvers.hpp] [player.hpp]   algorithms and game rules
        |
  [session.hpp]                          the shared "current state"
        |
  [console_ui.hpp]   [gui_app.hpp]       two ways to show it
                           |
                     [gui_window.hpp]    connection to the OS window
        |                  |
  [main.cpp]                             picks which one to start

Important design idea: gui_app.hpp never calls Windows. It draws
through an abstract class called Canvas (fillRect, fillCircle, drawText,
textWidth, textHeight). gui_window.hpp provides a Win32Canvas on Windows
and an X11Canvas on Linux. So the same drawing code works on both
systems; only the small Canvas classes differ. (This is the strategy
pattern / dependency inversion.)

The same idea is used for algorithms: MazeGenerator and MazeSolver are
abstract base classes. The UI holds a reference to "a generator" or
"a solver" and calls generate() or solve() without caring which one it
is. Adding a third solver only means writing one new class.

What happens when you click "4. Solve with BFS" in the window:

  1. Windows sends WM_LBUTTONDOWN to mazeLabWindowProc (gui_window.hpp)
  2. which calls app->onClick(x, y)                    (gui_app.hpp)
  3. onClick finds the button under the mouse and calls runAction(SolveBFS)
  4. runAction calls solve(session.bfsSolver)
  5. solve() runs BFS, stores the result, sets overlay to SingleSolution,
     and fills the info lines
  6. gui_window.hpp asks the window to repaint (InvalidateRect)
  7. WM_PAINT -> app->draw(canvas) draws the maze with path colours,
     the sidebar, the info box, and the legend

=== maze.hpp ========================================================

The maze is a grid of cells. Every cell starts with all four walls.
Generators knock walls down; solvers and the player can only move
between two cells when the wall between them is gone.

Direction           enum: Up, Right, Down, Left
allDirections[]     the four directions, for looping over neighbours

struct Coord        a position: row and col
  operator==, !=    compare two positions
  none()            the special value (-1, -1) meaning "no position"
  isNone()          true if this is that special value

struct Cell         one square of the grid
  wallTop, wallRight, wallBottom, wallLeft   true = wall is present
  visited           used only by the DFS generator
  reset()           put back all four walls and clear visited

class Maze
  init(rows, cols)  make a new grid of that size with all walls up.
                    Start is the top-left (0,0); end is the bottom-right
                    (rows-1, cols-1). Marks the maze as not generated.
  resetWalls()      put all walls back without changing the size
  rows(), cols()    size
  cellCount()       rows * cols
  start(), end()    start and exit positions
  isGenerated()     true after a generator has run
  markGenerated()   called by generators when they finish
  inBounds(pos)     true if pos is inside the grid
  cell(pos)         access the Cell at pos
  neighbour(pos, dir)  the position one step in that direction (may be
                       outside the grid; check with inBounds)
  hasWall(pos, dir) true if the cell at pos has a wall on that side
  openPassage(pos, dir)  remove the wall between pos and its neighbour.
                    Both cells store that wall (my Right = your Left),
                    so both sides are cleared. Does nothing at the edge.
  canMove(pos, dir) true if you can step from pos in that direction:
                    inside the grid, no wall, and the target is inside


=== disjoint_set.hpp ================================================

Disjoint set (also called union-find). Keeps track of which items are in
the same group. Each group is a tree; the root of the tree names the
group. Used by Kruskal's generator to know if two cells are already
connected. Items are numbers 0 .. size-1.

DisjointSet(size)   every item starts as its own group (its own parent)
find(x)             returns the root of x's group. Uses PATH COMPRESSION:
                    after finding the root, every item passed on the way
                    is pointed straight at the root, so later finds on
                    them are instant.
unite(a, b)         joins the groups of a and b. Returns false if they
                    were already in the same group. Uses UNION BY RANK:
                    the shorter tree is hung under the taller one so
                    trees stay shallow. (rank = an upper bound on height)
connected(a, b)     true if a and b are in the same group

With both tricks, find and unite take nearly constant time
(amortised O(alpha(n)), where alpha grows so slowly it is below 5 for
any realistic n).


=== generators.hpp ==================================================

class MazeGenerator (abstract base)
  generate(maze, rng)  build a maze inside "maze" using random numbers
                       from rng (std::mt19937)
  name()               display name

class DFSGenerator  -  "Randomized DFS" (recursive backtracker)
  generate():
    1. Put all walls up. Mark the start visited and push it on a stack.
    2. Look at the cell on top of the stack. Collect its unvisited
       neighbours.
    3. If there are none, it is a dead end: pop the stack (go back one
       cell) and repeat.
    4. Otherwise pick one at random, knock down the wall between them,
       mark it visited, and push it.
    5. Stop when the stack is empty: every cell has been visited.
  The stack replaces recursion, so large mazes cannot overflow the call
  stack. Produces long, winding corridors with few branches.

struct WallEdge     one inner wall: a cell and a direction (Right or Down)

class KruskalGenerator  -  "Kruskal's Algorithm"
  generate():
    1. Put all walls up.
    2. List every inner wall once: each cell's right wall (if not in the
       last column) and bottom wall (if not in the last row).
    3. Shuffle the list randomly.
    4. Every cell starts in its own region (DisjointSet).
    5. For each wall in shuffled order: if the cells on the two sides are
       in different regions, remove the wall and merge the regions
       (unite returns true). If they are already connected, keep the
       wall, because removing it would create a loop.
  Result: exactly one path between any two cells (a spanning tree).
  Produces many short dead ends and a more "even" texture.
  indexOf(maze, pos)  turns (row, col) into one number row*cols+col,
                      because the disjoint set works with numbers.


=== solvers.hpp =====================================================

struct SolveResult
  found              true if a path to the exit exists
  path               the cells from start to exit, in order
  expandedCells      every cell the solver took out of its queue, in order
  elapsedMicroseconds  how long the search took
  steps()            number of moves = path cells - 1 (0 if no path)
  cellsExpanded()    how many cells were expanded

class MazeSolver (abstract base)
  solve(maze)        starts a timer, calls search(), stops the timer,
                     stores the time in the result. Each solver only
                     writes search().
  name()             display name
  search(maze)       the actual algorithm (written by each subclass)
  buildPath(parentOf, start, goal, result)
                     each cell remembers the cell it was reached from
                     (its parent). Following parents back from the goal
                     gives the path in reverse; it is then flipped. If
                     the goal has no parent, no path was found.

class BFSSolver  -  "BFS"
  search():
    Uses a queue (first in, first out). Starts at the start cell. Takes
    the front cell, records it as expanded, stops if it is the goal,
    otherwise adds every reachable neighbour not seen before (parent is
    "none") to the back of the queue, remembering the parent.
  Because cells come out in order of distance from the start, the first
  time the goal comes out the path to it is a shortest path. BFS does not
  know where the goal is, so it spreads out evenly in all directions.

struct OpenEntry   one waiting cell in A*'s priority queue
  estimatedTotal   f = g + h
  costSoFar        g = steps from the start to this cell
  pos              the cell
  operator>        smaller f comes out first. On a tie, the bigger g
                   comes out first, because a cell further along is
                   probably closer to the goal.

class AStarSolver  -  "A*"
  search():
    Like BFS, but always expands the cell with the smallest f = g + h,
    using a priority queue (min-heap).
      g = steps taken so far
      h = manhattan(cell, goal) = |row difference| + |col difference|
    bestCost[r][c]  cheapest g found so far for each cell
    finalised[r][c] true once a cell has been expanded
    parentOf[r][c]  where we came from, for buildPath
    When a cheaper route to a cell is found, a new entry is pushed; the
    old, more expensive entry stays in the queue. So when a cell comes
    out that is already finalised, it is skipped ("lazy deletion").
  manhattan(a, b)  the fewest steps possible if there were no walls.
                   It never overestimates the real distance, so A* still
                   finds a shortest path, but it heads towards the goal
                   and usually expands fewer cells than BFS.

=== validation.hpp ==================================================

struct TestOutcome    a test's name and whether it passed

class ValidationSuite
  runAll()            runs the 13 tests (see section 8) and returns
                      the outcomes in order
  sizes               maze sizes tested: 2x2, 5x8, 10x10, 25x40
  seeds               random seeds tested: 1, 7, 42, 2026
                      (so 16 mazes per generator, and the same 16 every
                      time, which makes failures repeatable)

  Helper checks (each takes a maze and returns true/false):
  everyCellReachable  BFS flood from the start; counts reached cells and
                      compares with cellCount()
  wallsConsistent     for each pair of neighbours, my Right wall must
                      equal your Left wall, and my Down must equal your Up
  outerBoundaryClosed every wall on the outer edge is present
  openPassageCount    counts open passages (looks only Right and Down, so
                      each passage is counted once)
  pathIsValid         path exists, starts at start, ends at end, and each
                      step moves to a neighbour with no wall between
  forEveryMaze(generator, check)
                      generates a maze for every size and seed and returns
                      false as soon as one fails the check

  The test functions (generatorBuildsValidMaze, bothGeneratorsMakePerfect
  Mazes, ...) combine these helpers; see section 8 for what each proves.


=== benchmark.hpp ===================================================

runBenchmark(out)
  For each generator: builds 200 mazes of 50 x 50 with seeds 0 to 199,
  solves each with BFS and A*, and prints the averages:
    path       average shortest path length
    expanded   average cells expanded by BFS and by A*, and how many
               percent fewer A* expanded
    time       average microseconds for BFS and for A*
    length mismatches  how many mazes where BFS and A* path lengths
               differed (should always be 0)
  Fixed seeds mean the path and expanded numbers are identical on every
  run and every computer. Times change with the machine.

=== gui_window.hpp ==================================================

Plumbing between GuiApp and the operating system. You should not need to
edit it: colours, text and sizes are in settings.hpp, and what is drawn
is in gui_app.hpp. It does three things:
  1. opens a window (Windows: Win32 API, Linux: X11)
  2. gives GuiApp a Canvas that paints on it
  3. passes mouse clicks and key presses to GuiApp, then redraws

The file has three versions, chosen at compile time:
  #if MAZELAB_NO_GUI   runGuiWindow just returns 1 (no window support)
  #elif _WIN32         Windows version
  #else                Linux X11 version

Windows version:
  class Win32Canvas    implements Canvas with GDI (Windows graphics):
    constructor        creates the font (FONT_NAME, FONT_SIZE), makes
                       text backgrounds transparent, measures line height
    destructor         restores and deletes the font
    fillRect           CreateSolidBrush + FillRect
    fillCircle         Ellipse with a brush and no outline
    drawText           SetTextColor + TextOutA
    textWidth          GetTextExtentPoint32A
  mazeLabWindowProc    Windows calls this for every event ("message"):
    WM_NCCREATE        stores the GuiApp pointer inside the window
    WM_ERASEBKGND      ignored (prevents flicker)
    WM_PAINT           DOUBLE BUFFERING: draws the whole frame into an
                       off-screen bitmap first, then copies it to the
                       window in one step with BitBlt, so there is no
                       flicker
    WM_LBUTTONDOWN     mouse click -> app->onClick, then repaint
    WM_KEYDOWN         arrow keys -> app->onArrow, then repaint
    WM_CHAR            typed character -> app->onKeyChar, then repaint
    WM_DESTROY         window closed -> end the message loop
  runGuiWindow(app)    registers the window class, creates a fixed-size
                       window (WINDOW_WIDTH x WINDOW_HEIGHT inside the
                       borders), shows it, and runs the message loop
                       (GetMessage / DispatchMessage) until it closes.
                       Returns 0, or 1 if the window could not be made.

  Functions ending in "A" (CreateWindowA, TextOutA, ...) are the ANSI
  versions that take normal char strings. The "W" versions would take
  wide (Unicode) strings.

Linux (X11) version, same structure:

---------------------------------------------------------------------
6. THE ALGORITHMS EXPLAINED
---------------------------------------------------------------------

Think of the maze as a GRAPH: each cell is a node; an open passage
between two neighbouring cells is an edge.

PERFECT MAZE
  Every cell can be reached and there is exactly one route between any
  two cells (no loops). In graph terms it is a SPANNING TREE of the grid.
  A tree with N nodes always has exactly N - 1 edges, which is what
  test T3 checks.

RANDOMIZED DFS (generation)
  Idea: wander randomly, knocking down walls, and backtrack from dead
  ends. Uses a stack. Visits every cell once, so O(N) time for N cells.
  Long corridors, few branches, long solution paths.

KRUSKAL (generation)
  Idea: start with every wall up and every cell separate; remove walls
  in random order, but only when they join two separate regions.
  Never makes a loop, ends with one region. This is Kruskal's minimum
  spanning tree algorithm with random edge order instead of weights.
  O(E * alpha(N)) for the merging, plus the shuffle.
  Many short dead ends, shorter solution paths than DFS.

BFS (solving)
  Queue-based. Explores in "rings" of equal distance from the start, so
  the first path to reach the goal is a shortest path. O(N) time.
  Does not use the goal's position.

A* (solving)
  Priority-queue based. Expands the cell with the smallest f = g + h.
    g = real steps so far, h = Manhattan distance to the goal.
  h is ADMISSIBLE (never more than the true remaining distance), so A*
  still returns a shortest path. h makes A* prefer cells towards the
  goal, so it usually expands fewer cells. O(N log N) time because of
  the priority queue.

BFS vs A* in this project (from the benchmark, 200 mazes of 50 x 50):
  DFS mazes:      A* expands about 5.5% fewer cells than BFS
  Kruskal mazes:  A* expands about 27.9% fewer cells than BFS
  Both always find the same path length (0 mismatches).
  A* still took MORE time per maze on the development machine. Likely
  reasons: each priority-queue operation costs O(log n) instead of O(1),
  and A* keeps more arrays per cell. On DFS mazes the path winds so much
  that the Manhattan "hint" is often misleading, which is why the saving
  there is small.

DISJOINT SET (union-find)
  See disjoint_set.hpp in section 5. Path compression + union by rank.

8. THE VALIDATION TESTS
---------------------------------------------------------------------

Run with button "7. Run validation tests" (key 7) in the window, or option 8 in
the console. Each test runs on fixed sizes and seeds, so results are
repeatable.

  T1  DFS maze is complete and connected
      Every DFS maze is marked generated, every cell is reachable from
      the start, and walls are consistent.
  T2  Kruskal maze is complete and connected
      Same checks for Kruskal.
  T3  Perfect maze has cells - 1 passages
      Proves there are no loops (a connected graph with N nodes and N - 1
      edges is a tree).
  T4  Shared walls agree on both sides
      My Right wall equals my right neighbour's Left wall, and my Down
      wall equals the lower neighbour's Up wall. Catches a bug where
      openPassage clears only one side; T1 can miss that.
  T5  BFS path is valid
  T6  A* path is valid
      Path starts at start, ends at exit, and every step is a legal move.
  T7  BFS and A* path lengths match
      Evidence that A* with the Manhattan heuristic is still optimal.
  T8  Unreachable exit is reported
      On a maze with all walls up, both solvers say "no path".
  T9  Player is blocked by walls
      On a 3x3 maze with one opening, the player cannot move through a
      wall or off the grid, can move through the opening, and only legal
      moves are counted.
  T10 Smallest and narrow sizes work
      2x2, 2x10, 10x2, 2x3, 3x2: both generators and both solvers work.
  T11 Outer boundary stays closed
      Generators never knock down the outside wall.
  T12 Disjoint set find and unite
      Joining, rejecting a repeated join, and keeping separate groups
      separate.
  T13 Solvers do not change the maze
      After solving, every wall is exactly as before. (The solvers take
      the maze as const, so the compiler already enforces this; the test
      confirms it.)

What the tests do NOT prove: they check a fixed sample of mazes, not
every possible maze. Passing means these properties held on every
tested maze, which is strong evidence, not a mathematical proof.

10. KNOWN LIMITATIONS AND GOTCHAS
---------------------------------------------------------------------

  - The window has a fixed size and is not DPI-aware. On screens with
    display scaling, Windows enlarges it and the taskbar may cover the
    bottom. Lower WINDOW_HEIGHT if needed.
  - The info box holds about 6 lines.
  - Text uses the "A" (ANSI) Win32 functions, so non-English text
    (Hindi, emoji) will not display correctly in the window.
  - The X11 (Linux) version has not been tested on this machine.
  - Start is always top-left and exit bottom-right.
  - The window's - / + buttons move in steps of SIZE_STEP; the console
    (option 7) accepts any size from MIN_SIZE to MAX_SIZE.
  - Validation runs on fixed sizes and seeds, not on the maze currently
    shown on screen.
